# Decimal context analysis for finite integer powers

## Scope and result

This analysis covers the finite-integer-exponent branch of `PowerReal` in
`src/c47/mathematics/power.c`.  Nonintegral real powers and complex powers
remain separate audit targets.

For an integer exponent `n` with `|n| <= 999999999`, the implementation now
uses `decNumberPower` through the `realPower` wrapper at the caller's context.
The public real entry continues to supply `ctxtReal39`.  This is the narrowest
established fixed context among 34, 39, 51 and 75 digits.

Larger integer exponents retain the former logarithm/exponential route.  The
bound is symmetric because the project already provides the exact constant
`const_10p9__1`, and because it is wholly inside decNumber's dedicated integer
range.  This also preserves the existing behaviour for negative bases with
very large or infinite integer-valued exponents.

## Why the dedicated integer route is preferable

The former calculation evaluated

```
exp(n * ln(|y|))
```

and applied the sign afterwards for a negative base.  Even when `y^n` is an
exactly representable decimal, approximation error from `ln` and `exp` can
place the working result on one side of that exact value.  Directed final
rounding can then select the adjacent Real34 value.

For example,

```
3^70 = 2503155504993241601315571986085849
```

has exactly 34 digits.  The former route returned the next larger integer in
rounding modes 4 and 6.  Direct integer exponentiation returns the exact value
before the final conversion in every output mode.

The integer branch in decNumber uses binary exponentiation with balanced
internal rounding.  If the requested context has `p` digits and the exponent
has `d` integral digits, its accumulator has

```
p + d + 2
```

digits.  For this branch, `d <= 9`.  With `ctxtReal39`, the accumulator
therefore has 42 through 50 digits, and the library result is reduced to 39
digits before the selected 34-digit conversion.  decNumber documents a rare
maximum error of one ulp at the requested width for `power`; at 39 digits this
is below `1E-38` relative to a normal result.  Five decimal guard digits remain
before Real34 rounding.  Differences caused solely by the accepted 39-to-34
double rounding are outside this analysis.

The p39 exponent range also prevents a Real34-range event during the internal
calculation.  For a positive integer exponent, magnitudes generated by the
binary products do not exceed the more extreme of one and the final exact
magnitude.  For a negative exponent, decNumber first forms a guarded
reciprocal.  The wide p39 exponent limits contain every such finite Real34
case whose final value is representable.

## Why 34 digits are insufficient

The automatic `d + 2` extension does not turn a requested p34 result into a
universally faithful Real34 result.  Consider

```
y = 4.167496955017834746288349629
n = 716
```

Exact integer arithmetic forms the 19,776-digit coefficient of `y^n`.  Its
leading digits are

```
67718680442803198257781532343933134980283244243247...
```

so the correctly rounded 34-digit half-even value is

```
6.771868044280319825778153234393313E+443
```

A deliberate public-context reduction from p39 to p34 returned
`6.771868044280319825778153234393314E+443`, one Real34 ulp high.  The same
mutation failed the three nearest rounding settings in the file-driven cases.
The p39 route produced the independently derived result in all seven settings.

Contexts p51 and p75 reduce the already sub-Real34 working error, but provide
no demonstrated final-format benefit for this branch.  Thus p39 is the
narrowest supported choice from the project's existing contexts.

## Special values and compatibility

The public infinite-base handling precedes `PowerReal` and is unchanged.
Within `PowerReal`, zero exponents, zero bases, negative exponents and finite
negative bases inside the selected range use decNumber's integer semantics.
The former negative-base route remains active outside the selected range and
for infinite exponents, including its existing odd/even sign selection.

The change removes one logarithm, one multiplication and one exponential from
ordinary integer powers.  It also removes an unconditional desktop `fflush`
that existed only in the former negative-base calculation.

## Verification

The cases are part of the existing `src/testSuite/tests/power_real.txt` file.
They check the exact `3^70` result and the 716th-power p34 adversary under all
seven rounding settings.  Subtraction from independently computed Real34
values makes a last-digit error visible to the file-driven harness.

With the final cases present, the former implementation succeeds in 198 of
200 focused real-and-complex power checks; its two failures are the directed
exact-power cases.  The revised p39 implementation succeeds in all 200.  A
deliberate p34 public context succeeds in 197 of 200 and misses the 716th-power
case in all three nearest settings.

A clean complete `make test` run succeeds in all 15,168 checks with no GMP
allocation remaining.  The build emits only the established linker section
alignment warning.
